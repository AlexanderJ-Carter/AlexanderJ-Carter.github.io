深色模式已经是个人站标配，但实现分层很明显：有的站点切换丝滑；有的每次刷新都「闪白一下」再变黑，像灯管启动。后者在工程上往往只是脚本放错了时机，在观感上却像质量事故。

## 闪烁从哪来

典型顺序错误：

1. HTML 以浅色默认渲染；
2. CSS 与正文开始绘制；
3. 客户端 JS 读取 `localStorage` / `prefers-color-scheme`；
4. 给 `<html>` 加上 `dark` 类——画面猛地反色。

用户看到的是一次布局级闪烁（FOUC 的亲戚）。Wi-Fi 越慢，白屏停留越久，伤害越大。

## 正确姿态：绘制前决定

目标很简单：**第一帧就该是最终主题。**

常见做法是在 `<head>` 尽早放一段极小的同步脚本：读取存储与系统偏好，立刻设置 `html` 的 class 或 `data-theme`。它必须：

- 阻塞在正文绘制之前（刻意为之的小代价）；
- 不依赖大型框架 hydration；
- 失败时有明确回退（例如跟随系统）。

本站用 `html.dark` 约定，并有专门的主题脚本组件。改主题逻辑时，最怕的就是「为了干净把内联脚本挪到打包末尾」——干净了，闪烁也回来了。

## 存储什么、不存储什么

- 存：「用户显式选择了 light / dark / system」。
- 慎存：把每次系统变化都写成死值，导致用户改系统偏好后站点仍锁死旧选择。

若用户选 system，刷新时应重新读取媒体查询，而不是永远记住昨天的结果。

## 与 Tailwind / CSS 变量

深色不是简单反色。中性色阶、边框、代码块背景要成套设计。主题脚本只负责切换类名；真正的观感在设计令牌里。脚本再正确，色板对比度不够，深色模式依然失败。

## 无障碍与动效

切换主题时不要整页大幅闪动画。尊重 `prefers-reduced-motion`。按钮本身要有可访问名称（「切换深色模式」），不能只放一个看不懂的图标。

## 回归检查清单

改 Header 或布局后：

1. 硬刷新，系统为深色时是否首屏即深；
2. 手动选浅色后刷新是否保持；
3. 清存储后是否回退合理；
4. 无 JS（极端）时是否仍可读（至少一种默认主题）。

## 和广告、验证脚本的关系

主题脚本越早越好；第三方脚本越晚越好。不要把主题决定依赖分析或广告加载完成——它们失败时，用户仍应看到正确的深浅色。主题属于「阅读基础设施」，不是增值插件。

## 小结

主题无闪烁是个人站的「会不会收尾」信号。它不增加功能列表上的一项荣誉，但每次访问都在说话。把决定前移到绘制之前，把设计令牌做对，再把显式选择与系统偏好的语义分清——这三步通常就够了。
