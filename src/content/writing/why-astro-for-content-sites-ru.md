Главная поставка контентного сайта — слова и картинки в HTML, а не дерево состояния в браузере. Многие фреймворки по умолчанию предполагают, что «приложение должно жить в клиенте»; Astro — что «страница сначала документ, интерактив — островами по запросу». Для личных текстов, галерей и документации вторая гипотеза обычно проще — и легче выводит Core Web Vitals в зелёную зону.

## Чего контентные сайты боятся на самом деле

Ощущения читателя сводятся примерно к этому:

- **LCP**: как быстро читается самый крупный блок (часто заголовок или hero);
- **CLS**: не сдвигают ли шрифты и изображения вёрстку;
- **INP / задержка взаимодействия**: сколько ждать отклика после клика.

SPA может быть очень быстрой, но приходится ещё бороться с гидратацией, весом роутера и «тащить весь UI-runtime ради пары аккордеонов». На контентном сайте эта цена часто больше выгоды.

## Ответ Astro по умолчанию

**Нулевой JS на стандартном пути.** Компоненты на этапе сборки становятся HTML. Скрипт в браузер уходят только у островов с явным `client:*`.

Отсюда:

- списки статей, «обо мне», политика конфиденциальности — почти чистый документ;
- переключатель темы, плеер, мелкие инструменты — отдельные острова; при сбое страница остаётся читаемой;
- Total Blocking Time в лаборатории может быть близок к «нечему блокировать».

Я не обожествляю цифры — реальная сеть, шрифты, большие картинки и сторонние скрипты легко пробивают сотню. Но **архитектурно меньше JS** надёжнее, чем потом вырезать байты плагинами.

## Islands: интерактив по запросу, а не гидратация всего сайта

На этом сайте есть тема, проверочные ворота, инструменты, иногда плеер. Им место в островах, не в «весь сайт на React».

На практике я держусь:

1. **Если хватает CSS / нативного HTML — без компонента фреймворка.**
2. **`client:load` — дорогой дефолт; где можно — `visible` / `idle`.**
3. **Меньше островов на странице.** Пять маленьких тоже могут создать пробку.

## Статическая выдача и edge-кэш

`output: 'static'` (или эквивалентный пререндер) позволяет GitHub Pages / Cloudflare отдавать файлы как есть. Нет пути «запрос → БД → сборка страницы»; TTFB предсказуемее.

Контентный сайт обновляется как «написал статью — задеплоил» — идеально для SSG. Динамические формы можно отдать третьей стороне или edge-функции, не превращая весь сайт в SSR.

## Ямы, которые всё равно на вас

Astro сам не исправит:

- **большие картинки без размеров** — убийца LCP;
- **мигание шрифтов и переносы** — убийца CLS;
- **аналитика / чат / реклама «на всякий случай»** — убийцы INP и main thread;
- **клиентские переходы между маршрутами** — красиво, но стоит взвесить сложность.

На этом сайте уже есть заметка про оптимизацию производительности; эта — **почему такой фундамент реже оказывается медленным**, та — **что делать, когда уже медленно**.

## Когда не стоит насильно выбирать Astro

- тяжёлая realtime-коллаборация, сложные дашборды, плотное клиентское состояние;
- команда уже в экосистеме Next/Nuxt, а контент — приложение;
- плотность интерактива ближе к «приложению», чем к «документ + несколько виджетов».

Инструмент служит цели. Моя цель — личная мастерская на годы, текст и картинки в приоритете, скрипты сдержанно. Astro стоит на этой стороне.

## Что я реально экономлю по сравнению с «весь сайт на React»

Не «знать или не знать React», а:

- умственную нагрузку держать гидратацию согласованной для статического текста;
- регрессии при обновлении роутера и стейт-библиотек;
- runtime, который качают на слабом телефоне ради одного поста.

В островах я по-прежнему беру компоненты фреймворка — но путь по умолчанию — HTML. Асимметрия **документ дёшев, интерактив оплачен явно** для личного сайта очень выгодна.

Если 80 % страниц — статьи и справка, 20 % — мелкие инструменты, дефолты Astro на вашей стороне; если наоборот — пересмотрите выбор.

## Итог

Контентному сайту подходит Astro не из-за модного слова, а потому что поставка по умолчанию совпадает с читателем: сначала полный HTML, потом по запросу просыпаются острова. Core Web Vitals сами в зелёный не прыгнут — но одну войну «runtime фреймворка против документа» вы не ведёте. Правильные дефолты важнее правильного магазина плагинов.
