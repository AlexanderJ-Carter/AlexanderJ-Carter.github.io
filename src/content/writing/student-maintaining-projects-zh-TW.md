學生開發者最不缺的是靈感，最缺的是**下週仍想打開編輯器的理由**。課業、實習、睡眠輪流打斷節奏；GitHub 上因此堆滿 README 寫到一半的倉庫。

我維護本站與若干開源/研究相關貢獻時，逐漸相信：長期專案拼的不是爆發力，而是把「下次回來的成本」壓低。

## 先縮小到「冬天也能動」的範圍

立項時問三個問題：

1. **沒有新功能，只修文件與依賴，它是否仍有價值？**
2. **一個月只能擠出四個晚上，下一步最小交付是什麼？**
3. **我是唯一維護者時，哪些部分必須簡單到未來的自己能看懂？**

若答案依賴「暑假連續肝兩週」，專案結構就已經危險。個人站對我來說是好容器：它可以慢，可以薄更新，但網域與內容資產還在。

## README 與決策記錄比星星重要

後來者（包括三個月後的你）需要：

- 如何安裝、建置、部署；
- 目錄約定（例如本站：頁面邏輯在 templates，pages 只做薄包裝）；
- 明確的非目標（不做什麼），避免每次回來都重新辯論架構。

開源專案再補：Issue / PR 基本禮儀、授權條款、安全聯絡方式。華麗落地頁救不了沒有建置說明的倉庫；反過來，樸素但可執行的 README 能讓你在期末週仍然敢合併一小筆依賴升級。

## 用節奏代替心情

心情不可靠，節奏可以設計：

- **固定小步**：例如「每兩週至少一次：依賴修補或一篇短文或修一個 a11y 問題」。
- **發布可重複**：同一套 `npm run build` / `astro check`，減少「只有我這台機器能編過」。
- **變更可回看**：CHANGELOG 或清楚 commit，讓「上次改到哪」可見。

本站約束裡寫著提交前建置與檢查——這不是儀式，是給學生作息留的安全網：困的時候按清單走，少靠記憶。

## 開源貢獻：從小而可審的切片開始

參與實驗室或社群專案（例如文件、範例、邊界修復）時，學生常見誤區是一上來就啃大架構。更可持續的是：

- 先跑通開發環境與測試；
- 選有明確重現步驟的小問題；
- 讓 PR 描述寫清「為什麼」與驗證方式；
- 接受「這次只合併文件」也是貢獻。

社群認的是持續出現與可靠溝通，不是單次巨大 diff。

## 防止完美主義燒毀倉庫

「等設計系統完美再上線」會讓網域一直停在佔位頁。更健康的順序：

1. 可存取的最小站點；
2. 真實內容（哪怕三篇）；
3. 再打磨視覺與工具頁。

內容與信任頁（關於、聯絡、隱私）對讀者和平台審核都比又一個動畫重要。工具可以好玩，但不要讓工具頁比例壓過「這是有人在寫作與記錄的站」。

## 身心與邊界

長期維護包含：睡眠、眼睛，以及學會說「這個 issue 我做不了」。用愛發電可以，但把身體健康寫進維護策略裡——否則專案和人會一起停更。

## 期末週策略：維護模式開關

學期中段可以「功能模式」：加工具頁、改視覺、試新庫。一到考試週，強制切到「維護模式」：

- 只做安全修補與建置修復；
- 只合併已經寫到一半的文章，不開新大題；
- Issue 回覆範本化：「本週課業優先，預計 X 日後處理」。

這不是偷懶，是防止倉庫在壓力最大時被半成品拖死。公開說明節奏，比消失兩個月後再突然推一大坨更尊重協作者與讀者。

## 個人站作為「元專案」

本站對我來說不只是作品集，也是練習場：內容工作流、i18n、安全標頭、無障礙、部署都在同一倉庫裡迭代。它的好處是回饋快——改完建置，重新整理就能看。壞處是容易上癮加功能。

所以我把內容厚度寫進目標：工具可以少，文章與關於頁不能空。對學生開發者而言，能講清楚自己做了什麼，往往比再疊一個小遊戲更接近「可展示的能力」。

## 小結

學生身份不是減分，它只是提醒你：**時間塊更碎。** 於是專案要更小、文件要更勤、發布要更機械。個人站適合當這種訓練場——它允許慢，但要求你誠實對待讀者與未來的自己。能維護三年的小東西，往往比三個月的完美原型更接近工程師的日常。
