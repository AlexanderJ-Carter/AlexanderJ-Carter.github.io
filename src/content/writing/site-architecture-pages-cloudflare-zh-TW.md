有人問「你的站後端用什麼」。短答：多數時候沒有傳統後端。長答是這篇文章——從內容到建置，再到 GitHub Pages 與 Cloudflare 如何疊在一起。

## 目標形狀

我想要的個人站是：

- **便宜且耐放**：假期不維護也不應輕易掛掉；
- **快**：文件型頁面不該為框架水合付稅；
- **可稽核**：設定在 Git 裡，安全標頭與重新導向可審；
- **可演進**：以後加 Worker、加表單、加廣告，不必推翻重來。

於是選型收束到：Astro SSG + Git 託管建置產物/或 Pages 建置 + Cloudflare 在前面做 DNS、快取與防護。

## 建置期發生了什麼

本地或 CI 執行建置時，Astro 把：

- `src/pages` 路由；
- `templates` 裡的版面；
- `content/writing` 的 Markdown；
- `i18n` 文案；

編譯成一棵靜態檔案樹：HTML、CSS、少量 JS、圖片與 `public/` 下的原文（如 `ads.txt`、`_headers`、`.well-known`）。

沒有「請求到來再查資料庫渲染關於頁」。關於頁在建置時就已經是 HTML。

## GitHub Pages 的角色

倉庫本身是真相來源。GitHub Pages（或等價的靜態託管）負責把建置結果掛到網上。對個人專案，這很合適：權限模型熟悉、與 PR 工作流一致、成本可控。

要注意：

- 自訂網域與 HTTPS 憑證設定正確；
- `404` 與尾部斜線行為符合預期；
- 不要把金鑰寫進 Actions 日誌或公開變數。

## Cloudflare 的角色

網域前面的 Cloudflare 通常承擔：

- **DNS 與代理**；
- **邊緣快取與壓縮**；
- **WAF / 基礎 bot 管理**（按你的方案與規則）；
- **部分平台特性**：如 `_headers` 語意、重新導向、Workers（本站另有遺留重新導向等邏輯時）。

快取策略要心裡有數：HTML 與帶 hash 的資源應區別對待；更新文章後若看到舊頁，先查快取與部署是否完成，再懷疑建置。

## 動態能力放在邊緣，而不是硬塞進 SSG

聯絡表單、人機驗證、特殊重新導向，不必逼迫整站 SSR。常見模式是：

- 頁面仍靜態；
- 提交打到第三方或 Worker；
- 驗證門用客戶端工作階段標記（本站 About / Contact 的保護策略屬於這一類產品選擇）。

廣告腳本也是建置期開關：環境變數裡沒有 publisher id 就不注入，避免空殼請求。

## 我明確放棄的東西

- **執行時 CMS 強依賴**：寫作用 Markdown + Git，換編輯器自由，離線也可改。
- **為多語言強上重型 TMS**：五語 UI 已夠複雜，長文先把中文做厚。
- **把個人站做成微服務演示場**：能用靜態檔案解決的，不引入常駐程序。

## 故障時怎麼想

1. 建置綠了嗎？（`build` / `astro check`）
2. 部署到了正確分支/環境嗎？
3. Cloudflare 快取或規則是否卡住舊資源？
4. 是不是只有某一語言路徑 404？

分層排查比「重啟一下」有效。

## 成本與複雜度帳單

這套架構的月度現金成本可以接近於零（視流量與方案而定），但心智成本不是零：

- 你要理解 DNS、快取、Pages 建置日誌；
- 你要接受「沒有後台點一下就改文案」——改 Markdown、開 PR、等部署；
- 你要自己管安全標頭與依賴升級。

對我來說帳單划算，因為換來的是可控與可遷移：哪天換託管商，靜態檔案仍然是靜態檔案。若你更需要非技術編輯頻繁改稿，或許該在 SSG 之上加 Git 型 CMS，而不是一上來上資料庫。

## 和本站目錄的對應關係（簡圖）

- `src/content/writing`：長文；
- `src/components/templates`：頁面形狀；
- `src/pages`：薄路由；
- `public/`：原文資產與 `_headers`、`ads.txt`；
- Workers / 驗證：只包住真正需要動態的縫。

讀目錄比讀架構圖更快上手。新人（包括未來的自己）應能在一小時內找到「改首頁文案該去哪」。

## 小結

本站架構故意無聊：產生靜態檔案，放到可靠託管上，用 Cloudflare 做邊緣與防護。無聊換來的是——把時間花在文字、攝影與少量真正值得的互動上。若你也在搭個人站，先讓這條路徑跑通，再決定要不要 Worker、資料庫與推播通知。大多數時候，HTML 已經夠用。
