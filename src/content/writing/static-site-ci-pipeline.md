个人项目最常见的事故不是架构崩塌，而是：本地改了一点 i18n，忘了跑构建，推上去 Pages 挂了，自己还在地铁里。CI 不能让你更有创意，但能让你更早丢脸——在合并之前。

## 最小有用流水线

对 Astro 静态站，我认这三步：

1. **干净安装依赖**（锁定文件，可复现）；
2. **`astro check` / 类型与模板诊断**；
3. **`npm run build`**（真实生成静态产物）。

有余力再加：链接检查、Lighthouse CI、预览部署。但不要在还没有构建绿灯时，先堆十个漂亮 badge。

## 为什么本地绿不够

- Node 版本不同；
- 大小写敏感路径在 Linux CI 上爆雷（Windows / macOS 常放过）；
- 忘记提交的生成文件或环境变量；
- 只在某一语言路径下才触发的模板错误。

CI 用 Linux 干净环境跑一遍，是对「未来的自己」与协作者的保险。本站约束里把 build 与 check 写进提交前习惯；CI 则是习惯的自动执行。

## 与部署解耦

检查流水线与部署流水线可以分开：

- PR：只证明构建；
- `main`：构建通过后再发布，并按需清 CDN 缓存。

失败时让日志可读：哪一页、哪个集合条目出错。个人站没有值班团队，日志就是唯一同事。

## 别让 CI 变成戏服

- 允许跳过 hooks 的文化会迅速腐蚀质量；
- 把密钥写进 workflow 日志等于公开；
- 无意义的每日全量扫描浪费分钟数，也会让你学会无视红灯。

短、稳、与真实风险对齐——这就是好 CI。

## 学生作息下的额外好处

考试周你可以少开脑：改完推送，等绿勾，再关门。红了就看摘要，不必回忆「上一次手动构建的咒语」。自动化是对碎片时间的友好。

## 小结

静态站的 CI 目标不是企业级成熟度评分，而是一句话：**推上去的东西，默认可构建。** 先把安装、检查、构建做成每次必经之路，再考虑更炫的质量门禁。能在合并前失败，就是在对访客负责。
