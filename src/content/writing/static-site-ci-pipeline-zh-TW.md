個人專案最常見的事故不是架構崩塌，而是：本地改了一點 i18n，忘了跑建置，推上去 Pages 掛了，自己還在地鐵裡。CI 不能讓你更有創意，但能讓你更早丟臉——在合併之前。

## 最小有用流水線

對 Astro 靜態站，我認這三步：

1. **乾淨安裝依賴**（鎖定檔案，可重現）；
2. **`astro check` / 類型與範本診斷**；
3. **`npm run build`**（真實產生靜態產物）。

有餘力再加：連結檢查、Lighthouse CI、預覽部署。但不要在還沒有建置綠燈時，先堆十個漂亮 badge。

## 為什麼本地綠不夠

- Node 版本不同；
- 大小寫敏感路徑在 Linux CI 上爆雷（Windows / macOS 常放過）；
- 忘記提交的產生檔案或環境變數；
- 只在某一語言路徑下才觸發的範本錯誤。

CI 用 Linux 乾淨環境跑一遍，是對「未來的自己」與協作者的保險。本站約束裡把 build 與 check 寫進提交前習慣；CI 則是習慣的自動執行。

## 與部署解耦

檢查流水線與部署流水線可以分開：

- PR：只證明建置；
- `main`：建置通過後再發布，並按需清 CDN 快取。

失敗時讓日誌可讀：哪一頁、哪個集合條目出錯。個人站沒有值班團隊，日誌就是唯一同事。

## 別讓 CI 變成戲服

- 允許跳過 hooks 的文化會迅速腐蝕品質；
- 把金鑰寫進 workflow 日誌等於公開；
- 無意義的每日全量掃描浪費分鐘數，也會讓你學會無視紅燈。

短、穩、與真實風險對齊——這就是好 CI。

## 學生作息下的額外好處

考試週你可以少開腦：改完推送，等綠勾，再關門。紅了就看摘要，不必回憶「上一次手動建置的咒語」。自動化是對碎片時間的友善。

## 小結

靜態站的 CI 目標不是企業級成熟度評分，而是一句話：**推上去的東西，預設可建置。** 先把安裝、檢查、建置做成每次必經之路，再考慮更炫的品質門禁。能在合併前失敗，就是在對訪客負責。
