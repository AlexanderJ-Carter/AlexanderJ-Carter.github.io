有人问「你的站后端用什么」。短答：多数时候没有传统后端。长答是这篇文章——从内容到构建，再到 GitHub Pages 与 Cloudflare 如何叠在一起。

## 目标形状

我想要的个人站是：

- **便宜且耐放**：假期不维护也不应轻易挂掉；
- **快**：文档型页面不该为框架水合付税；
- **可审计**：配置在 Git 里，安全头与重定向可审；
- **可演进**：以后加 Worker、加表单、加广告，不必推翻重来。

于是选型收束到：Astro SSG + Git 托管构建产物/或 Pages 构建 + Cloudflare 在前面做 DNS、缓存与防护。

## 构建期发生了什么

本地或 CI 执行构建时，Astro 把：

- `src/pages` 路由；
- `templates` 里的版面；
- `content/writing` 的 Markdown；
- `i18n` 文案；

编译成一棵静态文件树：HTML、CSS、少量 JS、图片与 `public/` 下的原文（如 `ads.txt`、`_headers`、`.well-known`）。

没有「请求到来再查数据库渲染关于页」。关于页在构建时就已经是 HTML。

## GitHub Pages 的角色

仓库本身是真相来源。GitHub Pages（或等价的静态托管）负责把构建结果挂到网上。对个人项目，这很合适：权限模型熟悉、与 PR 工作流一致、成本可控。

要注意：

- 自定义域名与 HTTPS 证书配置正确；
- `404` 与尾部斜杠行为符合预期；
- 不要把密钥写进 Actions 日志或公开变量。

## Cloudflare 的角色

域名前面的 Cloudflare 通常承担：

- **DNS 与代理**；
- **边缘缓存与压缩**；
- **WAF / 基础 bot 管理**（按你的套餐与规则）；
- **部分平台特性**：如 `_headers` 语义、重定向、Workers（本站另有遗留重定向等逻辑时）。

缓存策略要心里有数：HTML 与带 hash 的资源应区别对待；更新文章后若看到旧页，先查缓存与部署是否完成，再怀疑构建。

## 动态能力放在边缘，而不是硬塞进 SSG

联系表单、人机验证、特殊重定向，不必逼迫整站 SSR。常见模式是：

- 页面仍静态；
- 提交打到第三方或 Worker；
- 验证门用客户端会话标记（本站 About / Contact 的保护策略属于这一类产品选择）。

广告脚本也是构建期开关：环境变量里没有 publisher id 就不注入，避免空壳请求。

## 我明确放弃的东西

- **运行时 CMS 强依赖**：写作用 Markdown + Git，换编辑器自由，离线也可改。
- **为多语言强上重型 TMS**：五语 UI 已够复杂，长文先把中文做厚。
- **把个人站做成微服务演示场**：能用静态文件解决的，不引入常驻进程。

## 故障时怎么想

1. 构建绿了吗？（`build` / `astro check`）
2. 部署到了正确分支/环境吗？
3. Cloudflare 缓存或规则是否卡住旧资源？
4. 是不是只有某一语言路径 404？

分层排查比「重启一下」有效。

## 成本与复杂度账单

这套架构的月度现金成本可以接近于零（视流量与套餐而定），但心智成本不是零：

- 你要理解 DNS、缓存、Pages 构建日志；
- 你要接受「没有后台点一下就改文案」——改 Markdown、开 PR、等部署；
- 你要自己管安全头与依赖升级。

对我来说账单划算，因为换来的是可控与可迁移：哪天换托管商，静态文件仍然是静态文件。若你更需要非技术编辑频繁改稿，或许该在 SSG 之上加 Git 型 CMS，而不是一上来上数据库。

## 和本站目录的对应关系（简图）

- `src/content/writing`：长文；
- `src/components/templates`：页面形状；
- `src/pages`：薄路由；
- `public/`：原文资产与 `_headers`、`ads.txt`；
- Workers / 验证：只包住真正需要动态的缝。

读目录比读架构图更快上手。新人（包括未来的自己）应能在一小时内找到「改首页文案该去哪」。

## 小结

本站架构故意无聊：生成静态文件，放到可靠托管上，用 Cloudflare 做边缘与防护。无聊换来的是——把时间花在文字、摄影与少量真正值得的交互上。若你也在搭个人站，先让这条路径跑通，再决定要不要 Worker、数据库与推送通知。大多数时候，HTML 已经够用。
