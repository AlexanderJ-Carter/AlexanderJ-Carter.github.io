內容站的核心交付物是 HTML 裡的字與圖，不是客戶端狀態樹。很多框架預設假設「應用要在瀏覽器裡跑起來」；Astro 預設假設「頁面先是文件，互動按需島嶼化」。對個人寫作、畫廊、文件型站點，後一種假設通常更省事，也更容易把 Core Web Vitals 做綠。

## 內容站真正怕什麼

讀者感受大致對應這幾項：

- **LCP**：最大那塊內容（常是標題區或 hero 圖）多久可讀；
- **CLS**：字體與圖片有沒有把版面頂來頂去；
- **INP / 舊式互動延遲**：點一下要等多久才有反應。

SPA 可以做很快，但你要額外對付：水合成本、路由庫體積，以及「為了幾個摺疊面板引入整套 UI 執行時」。內容站裡，這些成本經常大於收益。

## Astro 的預設答案

**零 JS 在預設路徑上。** 元件在建置期變成 HTML。只有你顯式加 `client:*` 的島嶼才會把腳本送到瀏覽器。

這意味著：

- 寫作列表、關於頁、隱私政策可以幾乎是純文件；
- 主題切換、音樂播放器、小工具單獨成島，失敗時也不拖垮整頁可讀性；
- Total Blocking Time 有機會接近實驗室裡的「沒什麼好堵的」。

我不會神話任何框架分數——真實網路、字體、大圖、第三方腳本隨時能把 100 分打穿。但**架構上少送 JS**，比事後用打包外掛摳體積更穩。

## Islands：互動按需，而不是全站水合

本站有一些互動：主題、驗證門、工具頁、偶爾的播放器。它們適合島嶼，不適合「整站 React」。

實踐裡我遵守：

1. **能 CSS / 原生 HTML 解決的，不上框架元件。**
2. **`client:load` 是昂貴預設，能 `visible` / `idle` 就延後。**
3. **一張頁面上的島越少越好。** 五個小島加起來也可能變成群島交通堵塞。

## 靜態輸出與邊緣快取

`output: 'static'`（或等價預渲染）讓 GitHub Pages / Cloudflare 這類 CDN 直接吐檔案。沒有「每次請求查庫拼頁面」的路徑，TTFB 更可預期。

內容站更新頻率通常是「寫一篇部署一次」，非常契合 SSG。動態表單可以走第三方或邊緣函式，不必為此把整站改成 SSR。

## 仍要自己管的坑

Astro 不會自動修好：

- **未約束尺寸的大圖**——LCP 殺手；
- **網頁字體閃爍與換行**——CLS 殺手；
- **隨手引入的分析 / 聊天 / 廣告腳本**——INP 與主執行緒殺手；
- **客戶端路由過渡**——好看，但要想清楚是否值得增加複雜度。

本站已經有一篇效能最佳化實錄；和這篇的關係是：那篇講「慢了怎麼修」，這篇講「為什麼選這個底座更不容易慢」。

## 什麼時候別硬選 Astro

- 重度即時協作、複雜儀表板、強客戶端狀態；
- 團隊已有完整 Next/Nuxt 元件生態且內容只是附屬；
- 你需要的互動密度已經接近「應用」，而不是「文件 + 少量控制項」。

工具服從目標。我的目標是：長期維護的個人工作室站點，文字與圖片優先，腳本克制。Astro 正好站在這一邊。

## 和「全用 React 做站」比，我實際省下什麼

不是省「會不會 React」，而是省：

- 為靜態文案維護 hydration 一致性的心智負擔；
- 為路由庫與狀態庫升級而做的回歸；
- 在低端機上為了打開一篇部落格而下載的執行時。

我仍會在島嶼裡按需用框架元件，但預設路徑是 HTML。這種不對稱——**文件便宜、互動顯式付費**——對個人站非常划算。

若你的站點 80% 頁面是文章與說明，20% 才是小工具，Astro 的預設值會站在你這邊；比例反過來，就該重新評估。

## 小結

內容站適合 Astro，不是因為潮流詞，而是因為預設交付物對齊讀者：先拿到完整 HTML，再按需喚醒島嶼。Core Web Vitals 不會因此自動滿分，但你少打一場「框架執行時 vs 文件」的仗。選對預設值，比選對外掛市場更重要。
