本站默认语言是简体中文，根路径 `/`；另有繁中、英式英语（`/en/`）、法语、俄语。多语言一开始很诱人——「国际范儿」——很快就会变成：同一句导航要改五个文件，一篇长文却只存在一种语言，搜索引擎还可能把重复页判得含糊。

这篇记录我实际采用的分层，以及故意不做的事。

## URL：子目录，默认语不加前缀

策略很普通，但有效：

- `zh-CN` → `/about/`
- 其他语言 → `/zh-TW/about/`、`/en/about/`、`/fr/about/`、`/ru/about/`

子目录共享主域权重，证书与部署也简单。默认语不加前缀，是为了让中文读者分享链接时更短，也符合「这是一个中文为主的站」的自我定位。

英式英语映射成 `/en/` 而不是 `/en-GB/`，是可读性与习惯的折中；`hreflang` 里仍声明正确的语言标签。

## 三种文案，三种住处

把所有字符串塞进一个巨型 `ui.ts` 会先爽后痛。本站大致分成：

1. **全局 UI**：导航、页脚、主题切换——`src/i18n/ui.ts`。
2. **页面文案**：首页、关于、隐私等——`src/i18n/pages/*.ts`，或模板顶部的 `Record<Lang, …>`。
3. **长文内容**：`src/content/writing/*.md`，目前以 `lang: zh-CN` 为主。

原则是：**改导航不碰文章；改文章不碰五种按钮文案。** 翻译工作按层推进，而不是要求「任何改动必须五语同步上线」。

未完成的语言页，宁可显示诚实的短说明（例如写作列表暂无该语言文章），也不要用机器翻译灌满重复薄内容——对读者与 AdSense 观感都不好。

## hreflang 与 canonical

每个重要页应：

- 有指向自身的 **canonical**；
- 在 `<head>` 提供各语言 **alternate hreflang**，外加 `x-default`（本站指向中文根）。

这不是装饰。没有它们，搜索引擎更难理解「这五页是同一文档的语言变体」。实现上应由布局根据当前路径批量生成，避免手写遗漏。

## 路由薄、模板厚

`src/pages/` 尽量只做包装：选定 `lang`，渲染对应 Template。页面结构与文案选择留在 `src/components/templates/`。

好处是：加一种语言时，主要是补翻译与路由包装，而不是复制整页业务逻辑。坏处是模板文件可能变长——需要靠页面级 i18n 文件把字符串继续外移。

## 翻译质量比覆盖率重要

多语言站常见失败模式：

- UI 全翻了，正文全是原文，切换语言像坏掉；
- 或正文机翻五份，语法通但气质无，还互相抢收录。

我更接受：**导航与法律页五语齐全，深度文章先把中文写厚。** 英文或其他语言作为后续增量，而不是申请广告前的灌水材料。

日期、数字、复数规则也要想到：法语、俄语的词形变化比「替换字符串」复杂。个人站阶段，能避免的动态句式就避免。

## 语言切换器的产品细节

- 切换后尽量留在「同一页面意图」（关于 → 关于），而不是一律回首页。
- 不要静默按 `Accept-Language` 强跳，打断分享链接；可提示，但尊重当前 URL。
- 在页脚或页头固定入口，避免藏进三级菜单。

## 内容不同步时怎么沟通

完全同步五语长文不现实。更诚实的产品表现是：

- UI 语言跟随切换；
- 若该语言暂无正文，明确提示并给出「阅读中文版」链接；
- 不要把自动翻译假装成人工译本。

搜索引擎与用户都讨厌「看起来有五语、点进去却是重复稀薄页」。缺译比假译安全。

## 工程上容易踩的坑

- 某语言漏了导航键，运行时回退到英文或空白；
- 只给默认语写了 `og:locale`，分享卡片语言错乱；
- 静态生成时忘记为某语生成路径，线上 404；
- 把用户生成内容与 UI 字符串混在同一文件，翻译时误改代码。

检查清单可以很短：新建一种语言时，打开首页、关于、一篇文章列表、隐私，四处点一点。

## 小结

多语言是信息系统，不是皮肤。先定 URL 与 hreflang，再定文案分层，最后才是「再加一种语言」。本站选择中文为根、其他语言前缀、长文按语言字段过滤——换的是可维护性，不是表面上的国旗图标数量。
