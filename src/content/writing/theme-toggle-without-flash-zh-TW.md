深色模式已經是個人站標配，但實作分層很明顯：有的站點切換絲滑；有的每次重新整理都「閃白一下」再變黑，像燈管啟動。後者在工程上往往只是腳本放錯了時機，在觀感上卻像品質事故。

## 閃爍從哪來

典型順序錯誤：

1. HTML 以淺色預設渲染；
2. CSS 與正文開始繪製；
3. 客戶端 JS 讀取 `localStorage` / `prefers-color-scheme`；
4. 給 `<html>` 加上 `dark` 類——畫面猛地反色。

使用者看到的是一次版面級閃爍（FOUC 的親戚）。Wi-Fi 越慢，白屏停留越久，傷害越大。

## 正確姿態：繪製前決定

目標很簡單：**第一幀就該是最終主題。**

常見做法是在 `<head>` 儘早放一段極小的同步腳本：讀取儲存與系統偏好，立刻設定 `html` 的 class 或 `data-theme`。它必須：

- 阻塞在正文繪製之前（刻意為之的小代價）；
- 不依賴大型框架 hydration；
- 失敗時有明確回退（例如跟隨系統）。

本站用 `html.dark` 約定，並有專門的主題腳本元件。改主題邏輯時，最怕的就是「為了乾淨把內聯腳本挪到打包末尾」——乾淨了，閃爍也回來了。

## 儲存什麼、不儲存什麼

- 存：「使用者顯式選擇了 light / dark / system」。
- 慎存：把每次系統變化都寫成死值，導致使用者改系統偏好後站點仍鎖死舊選擇。

若使用者選 system，重新整理時應重新讀取媒體查詢，而不是永遠記住昨天的結果。

## 與 Tailwind / CSS 變數

深色不是簡單反色。中性色階、邊框、程式碼區塊背景要成套設計。主題腳本只負責切換類名；真正的觀感在設計令牌裡。腳本再正確，色板對比度不夠，深色模式依然失敗。

## 無障礙與動效

切換主題時不要整頁大幅閃動畫。尊重 `prefers-reduced-motion`。按鈕本身要有可存取名稱（「切換深色模式」），不能只放一個看不懂的圖示。

## 回歸檢查清單

改 Header 或版面後：

1. 硬重新整理，系統為深色時是否首屏即深；
2. 手動選淺色後重新整理是否保持；
3. 清儲存後是否回退合理；
4. 無 JS（極端）時是否仍可讀（至少一種預設主題）。

## 和廣告、驗證腳本的關係

主題腳本越早越好；第三方腳本越晚越好。不要把主題決定依賴分析或廣告載入完成——它們失敗時，使用者仍應看到正確的深淺色。主題屬於「閱讀基礎設施」，不是增值外掛。

## 小結

主題無閃爍是個人站的「會不會收尾」信號。它不增加功能列表上的一項榮譽，但每次造訪都在說話。把決定前移到繪製之前，把設計令牌做對，再把顯式選擇與系統偏好的語意分清——這三步通常就夠了。
