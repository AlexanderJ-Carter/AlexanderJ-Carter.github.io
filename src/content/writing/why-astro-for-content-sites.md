内容站的核心交付物是 HTML 里的字与图，不是客户端状态树。很多框架默认假设「应用要在浏览器里跑起来」；Astro 默认假设「页面先是文档，交互按需岛屿化」。对个人写作、画廊、文档型站点，后一种假设通常更省事，也更容易把 Core Web Vitals 做绿。

## 内容站真正怕什么

读者感受大致对应这几项：

- **LCP**：最大那块内容（常是标题区或 hero 图）多久可读；
- **CLS**：字体与图片有没有把版面顶来顶去；
- **INP / 旧式交互延迟**：点一下要等多久才有反应。

SPA 可以做很快，但你要额外对付：水合成本、路由库体积、以及「为了几个折叠面板引入整套 UI 运行时」。内容站里，这些成本经常大于收益。

## Astro 的默认答案

**零 JS 在默认路径上。** 组件在构建期变成 HTML。只有你显式加 `client:*` 的岛屿才会把脚本送到浏览器。

这意味着：

- 写作列表、关于页、隐私政策可以几乎是纯文档；
- 主题切换、音乐播放器、小工具单独成岛，失败时也不拖垮整页可读性；
- Total Blocking Time 有机会接近实验室里的「没什么好堵的」。

我不会神话任何框架分数——真实网络、字体、大图、第三方脚本随时能把 100 分打穿。但**架构上少送 JS**，比事后用打包插件抠体积更稳。

## Islands：交互按需，而不是全站水合

本站有一些互动：主题、验证门、工具页、偶尔的播放器。它们适合岛屿，不适合「整站 React」。

实践里我遵守：

1. **能 CSS / 原生 HTML 解决的，不上框架组件。**
2. **`client:load` 是昂贵默认，能 `visible` / `idle` 就延后。**
3. **一张页面上的岛越少越好。** 五个小岛加起来也可能变成群岛交通堵塞。

## 静态输出与边缘缓存

`output: 'static'`（或等价预渲染）让 GitHub Pages / Cloudflare 这类 CDN 直接吐文件。没有「每次请求查库拼页面」的路径，TTFB 更可预期。

内容站更新频率通常是「写一篇部署一次」，非常契合 SSG。动态表单可以走第三方或边缘函数，不必为此把整站改成 SSR。

## 仍要自己管的坑

Astro 不会自动修好：

- **未约束尺寸的大图**——LCP 杀手；
- **网页字体闪烁与换行**——CLS 杀手；
- **随手引入的分析 / 聊天 / 广告脚本**——INP 与主线程杀手；
- **客户端路由过渡**——好看，但要想清楚是否值得增加复杂度。

本站已经有一篇性能优化实录；和这篇的关系是：那篇讲「慢了怎么修」，这篇讲「为什么选这个底座更不容易慢」。

## 什么时候别硬选 Astro

- 重度实时协作、复杂仪表盘、强客户端状态；
- 团队已有完整 Next/Nuxt 组件生态且内容只是附属；
- 你需要的交互密度已经接近「应用」，而不是「文档 + 少量控件」。

工具服从目标。我的目标是：长期维护的个人工作室站点，文字与图片优先，脚本克制。Astro 正好站在这一边。

## 和「全用 React 做站」比，我实际省下什么

不是省「会不会 React」，而是省：

- 为静态文案维护 hydration 一致性的心智负担；
- 为路由库与状态库升级而做的回归；
- 在低端机上为了打开一篇博客而下载的运行时。

我仍会在岛屿里按需用框架组件，但默认路径是 HTML。这种不对称——**文档便宜、交互显式付费**——对个人站非常划算。

若你的站点 80% 页面是文章与说明，20% 才是小工具，Astro 的默认值会站在你这边；比例反过来，就该重新评估。

## 小结

内容站适合 Astro，不是因为潮流词，而是因为默认交付物对齐读者：先拿到完整 HTML，再按需唤醒岛屿。Core Web Vitals 不会因此自动满分，但你少打一场「框架运行时 vs 文档」的仗。选对默认值，比选对插件市场更重要。
